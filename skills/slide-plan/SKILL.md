# slide-plan — 構想フェーズ

成果物は **構成案の Markdown 1 ファイル**（`<slug>.plan.md`）だけ。Marp のデッキはここでは書かない。
このファイルを `tech-slides` スキルが読んでスライドにする。

参照する知識：`../tech-slides/references/lessons.md`（過去の指摘。着手前に読む）、`../tech-slides/references/story-structures.md`（構成の型・枚数）、`layout-patterns.md`（図解の型。末尾に原典 39 パターンの対応表）、`assets.md`（画像が要る場面と取り方）、`design-principles.md`（1 枚の量）、`style-catalog.md`（見た目のテーマ 5 つと「〜みたいな」の対応表）。

## 姿勢

- **言いなりにならない。** ユーザーの案が聴衆にとって最適でないと思えば、理由と代案を出す。決めるのはユーザーだが、判断材料を出すのはこちらの仕事
- 聴衆の側から見る。「この枚を見た人は何を持ち帰るか」「前の枚から自然につながるか」を毎回問う
- 削る提案を恐れない。伝えたいことが多いほど、1 本の筋に絞るほうが伝わる。「これは Appendix に」「これは別の発表に」と言う
- 質問は 1 度に 1〜2 個、テキストで。ボタン選択は使わない。読み取れることは聞かない
- 数値・固有名詞・日付は推測で埋めない。分からないものは `<TBD>` にして一覧に載せる

## 進め方

### 0. 置き場所を決める（初回だけ聞く）

作業ファイルはカレントディレクトリに散らさず、**ユーザーが決めたワークスペースの下にデッキごとのディレクトリ**を切って置く。

```bash
bash "${TS}/scripts/workspace.sh" get          # 設定済みなら絶対パスが返る。未設定なら exit 1
bash "${TS}/scripts/workspace.sh" set ~/develop/slides   # 初回だけ。ユーザーが答えた場所を保存
bash "${TS}/scripts/workspace.sh" new <slug>   # <ws>/<slug>/ と assets/ を作る。以後の成果物はすべてここ
```
`${TS}` は tech-slides スキルのディレクトリ（プラグインなら `${CLAUDE_PLUGIN_ROOT}/skills/tech-slides`）。

- `get` が失敗したときだけ、「スライドはどのディレクトリの下に置きますか（例: `~/develop/slides`）」と **1 度だけ**聞いて `set` する。設定は `~/.config/tech-slides/config.json` に残り、次回からは聞かない
- `<slug>` は発表内容を表す短い英小文字（`cache-invalidation-2026`）。ユーザーが指定すればそれに従う
- 構成案は `<ws>/<slug>/<slug>.plan.md`。tech-slides もこの中に `<slug>.md`・PDF・`assets/` を置く
- 既にディレクトリがある話題の続き（修正・再構成）なら新しく切らず、そこを使う。`workspace.sh list` で一覧できる

### 1. 大雑把に聞く（1 往復）

ユーザーが伝えたいことを自由に話してもらう。渡された材料（記事・README・PR・メモ・過去のスライド）は全部読む。
次の 4 点が埋まるまで聞く。埋まっているものは聞かず「こう理解した」と一文で置く。

1. 用途と持ち時間（カンファレンス / 社内勉強会 / LT、何分）
2. 聴衆と前提知識（誰に、何を知っている人に）
3. 持ち帰り（聞き終えた人が明日できること、1 文）
4. 素材の有無（デモ、画面、計測結果、参考記事・動画）

見た目は **1 問だけ**聞く：「見た目は既定（明るい技術資料風 `tech-light`）でよいか、寄せたい雰囲気（例：ダークでコード主体 / 雑誌のような明朝 / 白地に太い活字のミニマル / 丸ゴシックでやわらかく）があるか」。
「〇〇みたいな」と返ってきたら `style-catalog.md` の対応表でテーマを決め、理由を一文添える。会場・用途から明らかなら聞かずに提案する（暗い会場・ライブコーディング → `tech-dark`、コミュニティ LT → `pop` など）。

### 2. 筋を決める（1〜2 往復）

`story-structures.md` の型（Why→What→How / 課題→試行→学び / 概念→例→反例 / 比較→基準→選定）から 1 つ提案し、理由を添える。
ここで **聴衆にとっての価値**を確認する：「この話を聞いて、聴衆の何が変わるか」が一文で言えなければ筋が立っていない。言えるまで練る。

判断の観点（ユーザーの案と違うときは、この観点で理由を言う）：
- 結論を先に出せているか（20 分以上なら冒頭 3 枚で「誰向け・ゴール・結論」）
- 枚数 × 1.5 分が持ち時間の 90% 以内か
- 「説明」ではなく「主張」が並んでいるか（「〜について」は主張ではない）
- 聴衆がすでに知っていることを長く話していないか
- デモ・コード・画面のうち、この聴衆に一番効くものが真ん中にあるか

### 3. 枚ごとに設計する（2〜3 往復）

各枚を「型・タイトル・リード文・根拠・素材」で書き出し、テキストで見せる。フィードバックを受けて直す。
- リード文は完全な一文で 1 行（全角 36 字目安）。図・画面だけで伝わる枚はリード文なしでよい（構成案に「リード: なし」と書く）。リード文も図も書けない枚は削る
- 型は `layout-patterns.md` の class 名で（`cols-3`、`compare.arrow`、`flow`、`stats`、`code`、`two+figure` …）。原典の番号で頼まれたら対応表から引く
- **素材**：画像が根拠になる枚（アプリ紹介 → 画面、ツール紹介 → ロゴ、記事・動画 → サムネイル）には必ず素材を書く。`assets.md` の表で判断する
  - 自分で取れるもの（ロゴ、公開ページの OG 画像・スクリーンショット、YouTube サムネイル）→「取得：こちらで」
  - 取れないもの（ログイン後の画面、ローカルアプリ、本人写真、実測データ）→「依頼：ユーザー」と、撮り方の条件
- 同じ型が 3 枚続いたら、どれかを別の型に変えるか統合する
- 文字だけの枚を 3 枚続けない。実画面・図・数値のどれかを 3 枚に 1 枚以上
- 「ノート」欄には口頭で言う内容を書く。スライドに載せない詳細はここに逃がし、`.note`（補足文）には出典 1 行以上を置かない
- ユーザーの下書きや他社資料を渡されたら、実画面・良い区分などの**要素**を取り込む。合意済みの構成を丸ごと寄せない。項目数を揃えるために実在しない項目を足さない
- 他者の取り組みへの評価語（地味・悲観的・遅れている）を書かない。その人が聴衆にいる前提で書く
- 箇条書きだけの枚が 3 枚以上あるなら、図解・コード・数値に置き換える候補を出す

### 4. 構成案ファイルを書く

`templates/plan-template.md` の形式で `<ws>/<slug>/<slug>.plan.md` を書き、パスを伝える。「出力先」欄にはそのディレクトリの絶対パスを書く。末尾に **素材リスト**（取得済み / こちらで取得 / ユーザーに依頼）と **TBD 一覧**を必ず付ける。
ユーザーに依頼する素材は、撮り方の条件（画面・状態・範囲・伏せる情報・保存名）まで書く。

最後に一文で「この構成案でスライド作成に進めてよいか。進めるなら tech-slides に引き継ぐ」と聞く。承認されたら、`tech-slides` スキルが `<slug>.plan.md` を読んで作る。

## 構成案ファイルの形式

`templates/plan-template.md` を見る。要点：

```markdown
# <発表タイトル>
用途 / 持ち時間 / 聴衆 / 前提知識 / 持ち帰り / 筋の型 / 想定枚数 / テーマ / 背景色 / 強調色

## 構成
### 1. [title] <タイトル>
- リード: <一文>
- 根拠: <何を見せるか>
- 素材: <ファイル名 or なし>（取得: こちら / 依頼: ユーザー / 取得済み）
- ノート: <話すこと・補足>
### 2. [rows] …

## 素材リスト
| # | 使う枚 | 何の画像か | 取得 | 条件・撮り方 | 保存名 | 状態 |

## TBD
- p1 の日付、p9 の計測値 …

## 検討の記録
- 却下した案とその理由（次回の再検討を防ぐ）
```

## やらないこと

- Marp のデッキ（スライド本体）を書く。図解の HTML を書く
- 聞かれていない見た目の細部（色・フォント）を議論する。テーマの選択は 1 問で済ませ、細部はテーマに任せる
- 骨子に「メッセージライン」「キャッチコピー」のような自己解説を書く
- 一度決めたことを蒸し返す（「検討の記録」に理由を残し、前に進む）

## 指摘を受けたら

構成の進め方や判断についてユーザーから指摘を受けたら、その場で直すだけでなく、一般化できる規則を `../tech-slides/references/lessons.md` の「進め方」に 1 行追記する。
